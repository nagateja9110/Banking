1. Project Overview
Brief Description
This project guides you through building a Banking / Fintech Application - a full-stack system that simulates the core operations of a digital bank. Users can open accounts, transfer funds, view transaction histories, and receive fraud alerts. Administrators can manage users, freeze accounts, and review audit logs. The project is built using Spring Boot (backend REST API), React (frontend), and MySQL (relational database), and is designed to mirror real-world fintech systems at companies like Razorpay, PhonePe, CRED, and Paytm.

Key Features
• User registration and login with JWT authentication (access token + refresh token)
• Account management: open SAVINGS or CURRENT accounts, check balances, view account status
• Fund transfers with full atomicity - both debit and credit happen in a single database transaction
• Transaction history with pagination, date filtering, and downloadable PDF statements
• Beneficiary management: save, verify, and delete payee accounts
• Fraud detection engine: flags suspicious transactions based on velocity, amount, and timing rules
• Audit logging using Spring AOP - every action is recorded with user, timestamp, and IP address
• Email notifications for logins, credits, debits, and flagged transactions
• Admin dashboard: view all accounts, freeze/unfreeze, review fraud flags, unlock accounts

Architecture (High-Level)
The application follows a classic 3-tier architecture with clear separation between layers:

Layer 1 - Frontend (React)React pages send HTTP requests to the backend via Axios. JWT tokens are stored in memory (not localStorage for security). Axios interceptors automatically attach the Bearer token to every request and silently refresh it when it expires. React Router guards routes based on user role.
Layer 2 - Backend (Spring Boot)The JWT filter intercepts every request, validates the token, and sets the SecurityContext. Controllers receive validated DTOs and delegate to the service layer. The service layer contains all business logic (@Transactional boundaries live here). Repositories are thin JPA interfaces. Spring AOP intercepts service calls to write audit logs without any manual logging code.
Layer 3 - Database (MySQL)All schema changes are managed by Flyway migrations. Account balances use DECIMAL(15,2) for precision - never use FLOAT for money. The @Version field on Account entities enables optimistic locking to prevent race conditions during concurrent transfers. Every fund transfer writes two ledger rows to the transactions table (debit + credit) - this is double-entry bookkeeping.

4. Concepts to Learn
Every concept below directly maps to code you will write. Read the brief, then implement it - that's how it sticks.

Backend Concepts
JWT Authentication (JSON Web Tokens)
A token-based auth mechanism where the server signs a token containing user info. The client sends this token with every request - the server verifies the signature and trusts the claims. No session storage needed on the server side (stateless).
Used in: AuthService, JwtUtil, JwtAuthFilter - login, token refresh, all protected endpoints
@Transactional and Database Transactions
A database transaction groups multiple SQL operations so they all succeed or all fail together (atomicity). Spring's @Transactional annotation handles this automatically. The isolation level controls how concurrent transactions see each other's data. SERIALIZABLE is the strictest - use it for money operations.
Used in: TransactionService.transfer() - the most important method in the entire project
Optimistic Locking with @Version
Prevents two concurrent updates from overwriting each other. JPA adds a WHERE version = ? to every UPDATE. If two requests try to update the same account simultaneously, the second one fails with OptimisticLockException and can be retried. This is lighter than database-level locking.
Used in: Account entity - protects the balance field from concurrent modification
Spring AOP (Aspect-Oriented Programming)
A way to add cross-cutting behavior (logging, security checks, transaction management) to methods without modifying the method itself. You define a Pointcut (which methods to intercept) and an Advice (what to do). @Around lets you run code before AND after a method, and even catch exceptions.
Used in: AuditAspect - automatically logs every @Auditable service method call
Idempotency Keys
A technique to safely retry API calls without causing duplicate effects. The client generates a unique UUID for each transfer request. If the request is submitted twice (due to network retry), the server detects the duplicate reference_id and returns the original result instead of executing the transfer again.
Used in: TransactionService - reference_id column with UNIQUE constraint
Double-Entry Bookkeeping
Every financial transaction creates two ledger entries: a debit on the sender's side and a credit on the receiver's side. The sum of all debits must equal the sum of all credits. This is how every real bank maintains financial integrity and allows auditing.
Used in: Transaction table design, TransactionService.transfer()
Security Concepts
BCrypt Password Hashing
A one-way hashing algorithm specifically designed for passwords. It is intentionally slow (to resist brute-force attacks) and automatically salted (so two identical passwords produce different hashes). Never store plain text passwords. Spring Security's BCryptPasswordEncoder handles this.
Used in: AuthService.register() - password hashing. AuthService.login() - password verification
AES-256 Encryption for PAN
Symmetric encryption for sensitive data at rest (PAN/Aadhaar numbers). Unlike hashing, encryption is reversible - you can decrypt to get the original value when needed. AES-256 uses a 256-bit key and is used by banks globally to protect PII (Personally Identifiable Information).
Used in: EncryptionUtil - encrypt on save, decrypt on read for PAN/Aadhaar fields
Rate Limiting
Controls how many requests a client can make in a given time window. Prevents brute-force login attacks, denial-of-service, and API abuse. Bucket4j implements a token bucket algorithm - each IP gets N tokens that refill over time. Requests that find no tokens available get a 429 Too Many Requests response.
Used in: Login endpoint rate limiting - 10 attempts per minute per IP
Frontend Concepts
Axios Interceptors
Middleware that runs before every request (to attach the JWT) and after every response (to handle 401 errors). When the access token expires, the response interceptor silently calls the refresh endpoint, gets a new token, and retries the original request - all transparently without the user seeing a login screen.
Used in: axios.js - request interceptor (attach token), response interceptor (handle 401 + refresh)
Zustand State Management
A minimal, hook-based state management library for React. Simpler than Redux - no reducers, actions, or boilerplate. You define a store as a single function with state and actions. Components subscribe to only the parts of state they need, and re-render only when those parts change.
Used in: authStore.js (user + tokens), accountStore.js (accounts list and selected account)

Pro Tip for Interviews

The single most important thing you can explain clearly: "Every fund transfer is wrapped in a single @Transactional boundary. If anything fails - validation, balance check, network issue - both the debit and credit are automatically rolled back by Spring, leaving both accounts unchanged. I also added optimistic locking with @Version on the Account entity so that if two transfers hit the same account simultaneously, only one succeeds and the other gets an OptimisticLockException - preventing a race condition where both see the same balance and double-spend." This one answer demonstrates you understand databases, concurrency, and system reliability - the three things fintech interviewers care most about.
